DWA Spiral Bug — root-cause & rollout plan

nav_full 시나리오에서 로봇이 spiral 돌고 EMERGENCY 고착되는 버그를 코드·설정 정합 검사로 추적한 결과, src/ 와 install/ 사이의 yaml 동기화 누락이 핵심 원인으로 드러났다. 본 보고서는 증상·원인·복구 절차를 한 페이지로 묶는다.

01한 줄 결론

Root cause — one line

src/amr_slam/config/amcl_params.yaml 은 이미 고쳐져 있지만, 실제 런타임에 로드되는 파일은 install/amr_slam/share/amr_slam/config/amcl_params.yaml(옛 버전)이라 수정한 값이 AMCL 에 적용되지 않고 있다. 메모리에 기록된 가설 (E) AMCL 미적용이 사실이었다 — AMCL 파라미터가 틀려서가 아니라 틀린 파일이 로드되고 있어서.

StatusUNRESOLVED 1주차 spiral bug, 3차 진단 시도 후 미해결 상태에서 본 보고서로 인계 Fix pathcolcon build --symlink-install --packages-select amr_slam amr_bringup amr_navigation + AMCL lifecycle restart Verifyros2 param get /amcl transform_tolerance 가 0.1 이면 1차 fix 적용 완료 RiskStep 1 후에도 잔존 시 §4 의 가설 2A → 2B → 2C 순으로 진행

02관측된 증상 — 메모리 + 코드 정합

dwa_node.py 에 2026-05-25 추가된 진단 로그 (tf_stamp_log_period, jump_warn_threshold 등) 가 캡처한 실측값:

지표 정지 시 이동 시작 직후 의미
TF stamp age ~20 ms 1248 ~ 3824 ms 모든 spiral 의 결정적 단서
DWA _state JUMP 0 0.3 ~ 3.6 m / cycle 50 ms 안에 텔레포트는 비물리적
best local_goal FRONT REAR 후방 trajectory 가 1등 → 후진 시작
cmd_vel (0, 0) (-1.0, -1.5) MAX 후진 EMERGENCY 직전 동작
/amcl_pose 외부 관찰 부드러움 부드러움 AMCL 자체 정상 — TF buffer 가 옛 값을 반환 중
AMCL 은 매장 안내 데스크 직원, EKF 는 매장 안의 카메라, DWA 는 손님이다. 카메라(EKF) 는 매끄럽게 손님 위치를 보내고, 안내 데스크(AMCL) 도 차분히 갱신하고 있다. 그런데 손님(DWA) 이 데스크에서 "지금 어디인가?"를 물을 때마다 데스크가 1초 전 위치를 유효한 답으로 알려주는 중이다. 1초면 1.5 m/s × 1 s = 1.5 m → 손님은 자기가 1.5 m 옆에 있는 줄 알고 반대 방향으로 출발한다.

03진짜 원인 — install 디렉토리 동기화 누락

증거 — 두 yaml 파일의 diff

SRC ros2_ws/src/amr_slam/config/amcl_params.yaml   — 이번 디버깅에서 수정한 파일 

update_min_d: 0.05              # 5cm 마다 pose 재추정
update_min_a: 0.05              # 2.9° 마다
transform_tolerance: 0.1        # 100ms 만 valid
transform_publish_period: 0.05  # 20Hz publish 강제

INSTALL ros2_ws/install/amr_slam/share/amr_slam/config/amcl_params.yaml   — 실제 런타임에 로드되는 파일 

update_min_d: 0.1               # 10cm 마다 (옛 값)
update_min_a: 0.1               # 5.7° 마다 (옛 값)
transform_tolerance: 1.0        # 1초간 valid (옛 값 — spiral 직접 원인)
# transform_publish_period 자체가 없음

왜 install 이 쓰이는가

launch 가 가리키는 경로
  • nav_full.launch.py 47줄: slam_share = FindPackageShare("amr_slam") → 항상 install/share/amr_slam 을 가리킨다 (src/ 아님).
  • localization.launch.py 24줄도 똑같이 get_package_share_directory('amr_slam') → 동일한 install 경로.
  • amr_slam/CMakeLists.txt 17~25줄의 install(DIRECTORY config launch DESTINATION share/${PROJECT_NAME}) 는 colcon build 시점에만 한 번 복사한다. --symlink-install 없이 빌드된 상태에서 src/yaml 만 고치면 install/yaml 은 옛 값 그대로.
요리 레시피를 노트북(src) 에서 고쳤지만, 정작 주방 벽에 붙어 있는 출력본(install) 을 안 바꿔서 주방장(AMCL) 은 옛 레시피로 계속 요리하고 있는 상황. 노트북을 아무리 고쳐봐야 음식은 똑같이 나온다.

05단계별 해결 절차

Step 01

install 디렉토리 재빌드 — 1차 원인 직격

RunPod 부팅 시퀀스 (메모리 project-runpod-boot) 후, 워크스페이스에서:

cd /workspace/opticore-amr/ros2_ws
colcon build --symlink-install --packages-select amr_slam amr_bringup amr_navigation
source install/setup.bash

WHY --symlink-install 옵션을 켜면 install/share 의 config/launch 가 src/ 의 심볼릭 링크가 된다. 다음에 yaml 만 수정하고 launch 다시 띄우면 즉시 반영 (재빌드 불필요). Python 노드도 src .py 가 직접 실행되므로 dwa_node.py 수정도 즉시 반영.

NOTE amr_navigation 도 같이 빌드 — install 의 dwa_node.py 동기화용. amr_bringup 은 ekf.yaml 동기화용.

Step 02

AMCL lifecycle 재시작 — yaml 적용 확실히

lifecycle_manager 가 autostart=True 라 build 후 launch 다시 띄우면 자동 적용되지만, 명시적으로 확정하려면:

# Pod 안에서 nav_full launch 띄운 직후
ros2 lifecycle set /amcl deactivate
ros2 lifecycle set /amcl activate
파일을 바꾼다고 메모리에 떠있는 프로세스가 자동으로 따라가지 않는다 — 컴퓨터 재부팅처럼 한 번 끄고 켜야 새 설정을 읽는다.
Step 03

파라미터 확인 — 실제로 바뀌었는지

ros2 param get /amcl transform_tolerance       # → 0.1 (1.0 아님)
ros2 param get /amcl transform_publish_period  # → 0.05
ros2 param get /amcl update_min_d              # → 0.05
ros2 param get /amcl update_min_a              # → 0.05

하나라도 옛 값(1.0 / 0.1) 이면 Step 1 이 안 먹은 것 — install/share/amr_slam/config/amcl_params.yaml 을 직접 열어 확인.

Step 05

(예방책) DWA lookup 을 interpolated TF 로 강제

dwa_node.py 에 이미 들어가 있는 tf_lookup_delay 파라미터를 활용. latest TF stale 회피:

ros2 param set /dwa_planner tf_lookup_delay 0.1

100 ms 과거의 안정된 interpolated transform 을 사용 → AMCL 갱신이 늦더라도 EKF 의 부드러운 TF chain 으로 보간된 값을 받음. 단점: 100 ms 만큼 명령 반응이 느려짐.

06검증 명령 — 메모리 기록 6개 (반드시 이 순서)

# Pod 띄우고 nav_full 띄운 직후 — 이 순서로 한 번씩
ros2 param get /amcl transform_tolerance       # 0.1 나와야 함
ros2 param get /amcl transform_publish_period  # 0.05 나와야 함
ros2 topic hz /odometry/filtered               # 50Hz
ros2 topic hz /clock                            # 1000Hz
ros2 topic hz /lidar                            # 10Hz
ros2 topic echo /odometry/filtered --once      # stamp vs sim_time 비교
메모리 인계

이 6개 명령은 project-dwa-spiral-bug 메모리에 "다음 세션의 첫 명령" 으로 명시됨. 하나라도 expected 와 다르면 거기서 일단 멈추고 가설을 좁힌 후 진행.

07Step 5 까지 했는데도 spiral 잔존 시 — 다음 가설 순서

  1. 가설 2C (clock lag) — ros2 topic hz /clock 가 1000 Hz 미만이면 Gazebo Real Time Factor 가 1.0 아래. 워크로드 (Pod CPU 점유) 줄이거나 Gazebo step_size 조정.
  2. 가설 2B (EKF stamp stale) — ros2 topic echo /odometry/filtered --once 의 header.stamp 와 ros2 topic echo /clock --once 의 sec/nanosec 비교. 100 ms 이상 차이 나면 EKF 입력 (/odom_with_cov 또는 /imu) 끊김 확인.
  3. scan stamp — ros2 topic echo /lidar --once 의 header.stamp 가 옛 sim_time 인지. likelihood_field model 은 scan stamp 시점의 TF 로 매칭하기 때문에 stamp 자체가 옛것이면 AMCL pose 도 옛것.
  4. AMCL recovery 가속 — particle filter 가 발산 후 회복 못 하는 경우. recovery_alpha_fast: 0.2, recovery_alpha_slow: 0.005 로 더 빠르게.
